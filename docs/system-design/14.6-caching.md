# 14.6 Caching Strategies & Architectures

```mermaid
flowchart TD
    User[Client Browser] -->|1. Browser Cache / LocalStorage| Hit1[Instant Local Render]
    User -->|2. Edge Cache Miss| EdgeCDN[Cloudflare CDN Edge Cache]
    EdgeCDN -->|3. CDN Cache Miss| AppServer[API Server Cluster]
    AppServer -->|4. Redis Query: GET reviews:top20| Redis[(Redis In-Memory Cache)]
    Redis -->|Cache Hit (1 ms)| AppServer
    Redis -.->|5. Cache Miss| Postgres[(PostgreSQL Database)]
```

---

## 1. What It Is in Plain Words
Caching stores copies of frequently accessed data in high-speed storage layers (RAM, SSD, Edge CDN) to eliminate repetitive database queries and reduce latency.

---

## 2. Whether & How THIS Project Uses It
- **Current Implementation**:
  - **Browser HTTP Cache**: Caches external font files and stylesheet assets.
  - **In-Memory JavaScript Cache**: Caches `testimonials` array in RAM during page lifecycle ([`testimonial.js:16`](file:///Users/avishjain/avishjain9-repos/53-testimonials-grid/testimonial.js#L16)).
  - **DOM Element Cache**: Top-level selectors (`imagePreview`, `scrollerTrack`) queried once on initialization.

---

## 3. Scale Suitability Evaluation
For a client-only single-page app, memory caching is the fastest possible strategy ($O(1)$ RAM access). [CONFIRM WITH DEVELOPER]

---

## 4. Full Alternatives Comparison

| Caching Layer | Medium | Latency | Eviction Policy | Invalidation Strategy | Best Fit |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **JS Heap Memory (Chosen)** | Client RAM | **< 0.1 ms** | Garbage Collection | Immediate mutate | **Single-page client state** |
| **Browser LocalStorage** | Client Disk | 2-5 ms | Manual / Quota | Immediate rewrite | Offline client persistence |
| **Edge CDN Caching** | Edge SSD / RAM | 10-25 ms | TTL / Stale-While-Revalidate| Purge on publish | Static assets & public reviews |
| **Redis Cluster (Proposed)**| Server RAM | 1-2 ms | LRU / TTL | Cache-Aside on write | Centralized cloud review feed |
| **Database Query Cache** | DB Buffer Pool | 2-5 ms | Clock sweep | Automatic on table write | Ad-hoc query speedup |

---

## 5. Trade-offs Accepted
Memory cache is lost on page refresh; recovered by reading from LocalStorage.

---

## 6. What Breaks First at Scale
- **10x Load**: No breakage.
- **100x Load**: Without Redis, concurrent read traffic hits PostgreSQL directly, exhausting connection pools.
- **1000x Load**: Cache stampede (thundering herd) if the primary review cache key expires under heavy load.

---

## 7. How a Senior Engineer Would Improve It
Implement a **Cache-Aside pattern with Redis**:
1. Check Redis for `reviews:feed:v1`.
2. On miss, query PostgreSQL, populate Redis with a 5-minute TTL, and add randomized jitter to prevent thundering herd.
3. On new review submission, publish an invalidation event to clear the Redis key.

---

## 8. 30-Second Spoken Interview Answer
> "We employ a multi-tier caching hierarchy. In the browser, we cache the active reviews array in JavaScript memory for sub-millisecond DOM updates, backed by LocalStorage for offline persistence. In our cloud architecture, we would place a Redis cache-aside layer in front of PostgreSQL to serve the top twenty reviews marquee feed, absorbing 99% of read traffic without touching the database."
